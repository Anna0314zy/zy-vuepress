# 工程能力体系分析

## 1. 维度框架

从 **交付效率、质量保障、可运维性、协作治理** 四维度审视 ICW Creator 当前工程体系，并标注证据来源（依赖与目录形态）。

## 2. 交付效率

### 2.1 Monorepo 与依赖管理

- **pnpm workspace**：减少磁盘占用与安装时间，支持 workspace 协议精确绑定内部包版本。
- **脚本**：根级 `load:app-deps` 组合 `release-tool`，说明 Widget/扩展资产的加载已纳入标准开发路径，降低「新人漏步骤」成本。

### 2.2 构建工具矩阵

- **多样性与摩擦**：同时存在 CRA 系脚本（editor）、craco（player-v2）、tsup（render-engine-cocos2）、tsdx（schema）、esbuild（sl-conversion）。好处是各包可选最优工具；代价是 **心智与模板碎片化**，新人上手曲线陡峭。

### 2.3 版本与发布

- **standard-version**、**semantic-release** 家族依赖并存，提示发布自动化意愿强烈，但需 **单一准则** 防止双轨。

**能力评级（主观）：** 中高——Monorepo 与分包构建成熟；统一构建编排仍有收敛空间。

## 3. 质量保障

### 3.1 静态检查

- **ESLint + Prettier + lint-staged + husky**：提交前格式化与常规规则具备。
- **functional eslint 插件**（根 devDependencies）：暗示团队关注 **不可变与副作用风格**（具体启用范围视配置而定）。

### 3.2 测试

- `@testing-library/*` 出现在根 devDependencies；各 app 测试脚本仍以 CRA/Jest 模板为主。**隐性缺口**：schema 迁移与 player-sdk 服务层若缺少 golden test，回归成本高。

### 3.3 契约与类型

- `@icw/schema` 配置 **size-limit**，体现对 **包体积回归** 的关注；`@icw/typing` 提供共享类型，利于 TS 跨包一致性。

**能力评级：** 中等——基建齐全；关键路径（迁移、渲染协议）需加强自动化测试金字塔中层。

## 4. 可运维性

### 4.1 运行时观测

- **Sentry** 多端引入：编辑器与 Player 具备错误上报入口。

### 4.2 Serverless

- `sl-conversion` 使用 logger、告警通知；符合 **故障可感知** 起步要求，待补强指标大盘。

### 4.3 依赖补丁

- **patch-package** 说明工程允许紧急修补上游；需配套 **补丁生命周期管理**，否则阻碍升级。

**能力评级：** 中高——线上异常有抓手；云函数与多端组合需统一 traceId。

## 5. 协作治理

### 5.1 提交规范

- **commitlint + conventional config**：利于 changelog 与代码考古。

### 5.2 文档资产

- 仓库内含 `.qoder/repowiki` 等结构化文档，利于 onboarding（需注意与源码同步）。

### 5.3 代码所有权

- Monorepo 建议配套 **CODEOWNERS**（若未在摘录中出现，列为改进项）：按 `packages/schema`、`services/sl-conversion` 分配审查责任。

**能力评级：** 中等偏上。

## 6. 综合结论与补强优先级

| 补强项 | 说明 |
|--------|------|
| 统一构建/测试编排 | 降低 app 间脚本差异 |
| Schema 迁移测试矩阵 | 防止协议演进回归 |
| Affected CI | 缩短 PR 周期 |
| 单一版本发布策略 | 降低 registry/tag 混乱 |
| OpenSSL/webpack 升级专项 | 解除 Node 升级阻断 |

**Overall：** 具备中大型前端平台工程的骨架（Monorepo、契约包、多端、Serverless），工程成熟度由 **测试覆盖率与基建升级债务** 共同约束上限。

# 深度问答拆解（含标准答案）

本章针对架构评审中常见的 **追问链（follow-up chain）**，每一题给出「面试官意图 → 拆解思路 → 结合本项目的落地表述 → 反例与边界」。

---

## D1：你说 Schema 是协议层，那「协议演进」和「功能发布」如何对齐？

**面试官意图：** 考察是否理解 **兼容性矩阵** 与 **渐进交付**，而非仅会写迁移函数。

**拆解思路：**

1. 区分 **读取兼容**（新播放器读旧数据）与 **写入兼容**（新编辑器产出的数据能否被旧播放器读）。
2. 引入 **版本协商**：播放器启动时读取 `page.version`，决定是否走迁移管道。
3. 定义 **弃用周期**：旧版本播放器占比低于阈值后才删除迁移分支。

**结合本项目：** `@icw/schema` 已具备 `getLatestVersion`、`updateToLatest`、`backToOldVersion`，工程补齐点是：**线上观测各版本占比**、**迁移失败采样**、以及发布 checklist 要求「descriptor / typing / versions 三改同 PR」。

**反例：** 仅升级编辑器不写迁移，导致云端一半资产校验失败；或删除旧迁移函数导致无法打开历史课件。

## D2：`realTimeSave` 为什么不直接用 React `useEffect` 监听状态？

**面试官意图：** 考察 **关注点分离** 与 **副作用放置层级**。

**拆解思路：**

- `useEffect` 适合组件局部副作用；自动保存是 **跨页面的全局策略**，散落在组件会导致重复订阅、遗漏卸载、测试困难。
- Redux 中间件对 **所有符合条件的 action** 统一生效，天然 **集中策略**。

**结合本项目：** 白名单 `main` 命名空间体现「仅核心课件模型触发保存」的产品假设；风险是业务 refactor 改名 namespace 时漏改白名单。

**边界：** 若保存逻辑需要 UI 上下文（例如「仅当 Modal 关闭后保存」），中间件难以表达，应退回 **command 层显式 orchestrate** 或引入 saga 风格流程。

---

## D3：独立渲染应用与编辑器通信，你如何避免「协议碎片化」？

**面试官意图：** 考察 **RPC/消息 schema** 与 **版本握手**。

**拆解思路：**

1. 单一 **消息信封**：`{ v, type, payload, traceId }`。
2. **类型定义共享**：消息 DTO 放在 `packages/*`，禁止各 app 手写字符串常量。
3. **兼容策略**：`v` 不匹配时降级或拒绝并提示升级。

**结合本项目：** 已有 `@icw/typing` 与 schema 双向约束的倾向；渲染侧若使用 socket.io，则需同样对 server push 定义 schema，否则易出现「引擎私有字段泄漏到编辑器」。

## D4：Monorepo 下如何做「按需发布」与回滚？

**面试官意图：** 考察 **发布工程学**，不仅是代码组织。

**拆解思路：**

1. **变更检测**：计算 affected packages。
2. **版本策略**：固定版本（CalVer/SemVer）与 tag；私有 registry  promotion。
3. **回滚**：registry 回退 artifact + 配置开关；若仅有前端静态资源，CDN 回源版本。

**结合本项目：** `semantic-release-monorepo` 暗示自动化意愿；需明确 **player-v2 与 editor 是否同版本号**，避免线上组合未经测试。

## D5：Serverless 转码失败为什么要打 Lark？还有什么更好的观测手段？

**面试官意图：** 考察 **可观测性分层**：告警 vs 指标 vs 日志。

**拆解思路：**

Lark 适合 **人介入异常**；但不替代指标。完整方案应包含：（1）**结构化日志**（taskId、resourceCode、step、duration）；（2）**指标**：成功率、P95 耗时、冷启动率；（3）**Tracing**：跨 notify 回调的全链路 ID；（4）告警 **限速与聚合**。

**结合本项目：** `sl-conversion` 已在 catch 路径拼装 Lark 文本；演进项是把同一任务的多条告警折叠，并暴露 Prometheus 类指标供自动扩容决策。

---

## D6：渲染引擎依赖 `socket.io-client`，如果换成原生 WebSocket 会怎样？

**面试官意图：** 考察 **传输层选型** 与 **fallback**。

**拆解思路：**

Socket.IO 提供 **心跳、重连、packet 复用、命名空间**；纯 WebSocket 需自建帧协议与重连状态机。若服务端已是 Socket.IO，强行替换客户端会破坏兼容。

**结合本项目：** 应先厘清服务端是否为 Socket.IO 协议；若是，不宜仅为包体积替换客户端，除非服务端同步迁移。

---

## D7：编辑器引入 FFmpeg.wasm，安全和性能你怎么兜底？

**面试官意图：** 考察 **WASM 资源隔离** 与 **主线程让步**。

**拆解思路：**

1. **来源可信**：仅允许处理用户明确选择的本地文件或签名 URL。
2. **内存上限**：限制输入大小与并发任务数。
3. **Worker**：避免阻塞 UI；进度回调节流。
4. **COOP/COEP**：若启用跨域隔离，需核对静态资源与 COS 响应头。

---

## D8：Player 使用 COS SDK，如何做密钥安全？

**面试官意图：** 考察 **前端凭证模型**。

**拆解思路：**

浏览器不应长期持有 **永久密钥**；应使用 **STS 临时凭证** 或 **后端签名 URL**。评审追问：凭证刷新策略、时钟偏移、以及课堂弱网下的重试。

---

## D9：为何仓库里存在 `patch-package`？长期策略是什么？

**面试官意图：** 考察 **依赖治理**。

**拆解思路：**

补丁说明上游缺陷或业务特例短期无法接受上游节奏。长期策略：（1）向上游 PR；（2）fork 维护；（3）替换依赖。每项补丁需 **ADR（Architecture Decision Record）** 记录原因与移除条件。

**结合本项目：** `dom-to-image`、`whatwg-fetch` 等补丁需要在依赖升级时执行 **回归矩阵**（导出截图、播放器 fetch 路径）。

---

## D10：若要做多人实时协作编辑，现有架构从哪里开刀？

**面试官意图：** 考察 **CRDT/OT** 与 **现有 Redux 模型** 的融合。

**拆解思路：**

1. **文档模型**：课件树是否适合 CRDT（富文本、绝对坐标组件可能冲突复杂）。
2. **传输**：WebSocket 同步 ops；服务端权威序列化。
3. **本地状态**：Rematch 变为「本地投影」，中间层同步 adapter。
4. **与 `realTimeSave` 关系**：协作保存应是 **periodic snapshot + op log**，而非每个本地 action 直接打满 HTTP。

**结合本项目：** 现有中间件偏「单机自动保存」；协作需引入 **会话层** 与 **冲突 UI**，属于架构级增量而非单 PR。

## 一、五种模式详解

### 1. Network（网络型）
- **核心逻辑**：完全去中心化，每个智能体都可以直接和其他任何智能体通信，自己决定下一步调用谁。
- **特点**：自由度最高，没有固定流程，像一个完全开放的社交网络。
- **适用场景**：需要动态协作的复杂任务，比如多个 Agent 自发分工完成一个创意项目。
- **风险**：可能出现循环调用、状态混乱，调试难度高。

### 2. Supervisor（主管型）
- **核心逻辑**：设置一个“主管智能体”，所有子 Agent 都只和主管通信，由主管决定下一步调用谁。
- **特点**：中心化调度，流程可控，调试方便，是最常用的模式之一。
- **适用场景**：任务有明确分工，比如“需求解析 → 图形生成 → 渲染 → 校验”，主管负责按步骤调度。

### 3. Supervisor as Tools（主管工具调用型）
- **核心逻辑**：主管架构的简化版，把每个子 Agent 包装成工具，主管用支持工具调用的 LLM 来决定调用哪个“工具 Agent”。
- **特点**：实现非常简单，利用 LLM 原生的工具调用能力做调度，不用自己写复杂的分支逻辑。
- **适用场景**：快速搭建多 Agent 系统，比如把“生成、渲染、校验”都做成工具，让 LLM 自己决定什么时候调用。

### 4. Hierarchical（层级式）
- **核心逻辑**：多层级的主管架构，像公司组织架构一样，每个层级都有自己的主管。
  ```
  顶层主管（GM） → 中层主管（总监） → 基层主管（组长） → 执行Agent（员工）
  ```
- **特点**：分工更细，层级清晰，适合超大规模的复杂系统。
- **适用场景**：复杂多模块项目，比如一个编辑器系统里，有“图形模块主管”“文本模块主管”“导出模块主管”，再由顶层主管统一调度。

### 5. Custom（自定义型）
- **核心逻辑**：用 LangGraph 的条件边、子图等能力，完全自定义流程。
- **特点**：最灵活，没有固定模式，可以根据业务需求设计任意执行流，实际项目中使用最多。
- **适用场景**：业务逻辑复杂、需要特殊流转规则的场景，比如带分支、循环、重试的编辑器工作流。

---

## 二、模式对比与选型建议
| 模式 | 实现复杂度 | 可控性 | 调试难度 | 推荐场景 |
| :--- | :--- | :--- | :--- | :--- |
| Network | 高 | 低 | 高 | 动态无固定流程的创意任务 |
| Supervisor | 中 | 高 | 中 | 分工明确的流水线任务 |
| Supervisor as Tools | 低 | 中 | 低 | 快速验证、轻量多Agent系统 |
| Hierarchical | 高 | 高 | 中 | 大规模、多层级的复杂系统 |
| Custom | 中 | 极高 | 中 | 业务逻辑特殊、需要完全自定义流程 |

## 三、和你的编辑器项目的适配
你的图形编辑器项目，用哪种模式最合适？

### 推荐方案：Supervisor as Tools + 自定义条件边
1.  **用 Supervisor as Tools 做核心调度**：
    - 把“需求解析、图形生成、参数校验、SVG渲染”都包装成工具Agent；
    - 主管LLM根据用户指令，自动决定调用哪个Agent、传递什么参数。
2.  **用自定义条件边做特殊流程**：
    - 比如“校验失败 → 重试生成”“用户修改指令 → 回溯到生成步骤”等分支逻辑，用LangGraph的条件边实现。

### 为什么不选其他模式？
- Network：你的流程有明确的业务顺序，不需要完全去中心化的协作；
- Hierarchical：目前项目规模不大，多层级架构会增加不必要的复杂度；
- 纯Custom：从零写流程调度成本太高，不如用工具调用型主管快速搭建。

## 四、极简实现示例（Supervisor as Tools）
```python
from langchain_openai import ChatOpenAI
from langchain.tools import tool
from langgraph.prebuilt import create_react_agent

# 1. 把每个子Agent包装成工具
@tool
def generate_shape(prompt: str) -> str:
    """根据用户描述生成图形参数"""
    return f"生成了矩形，颜色：红色"

@tool
def render_svg(params: str) -> str:
    """根据图形参数渲染SVG"""
    return "<rect fill='red' />"

# 2. 创建主管Agent（带工具调用能力）
llm = ChatOpenAI(model="gpt-3.5-turbo")
supervisor = create_react_agent(llm, tools=[generate_shape, render_svg])

# 3. 运行
supervisor.invoke({"messages": [{"role": "user", "content": "生成一个红色矩形"}]})
```

---
这是 LangGraph 多智能体协作里一个非常核心的模式——**Handoff（任务移交）工具工厂**，它解决了「智能体之间如何安全、规范地转交任务」的问题。我帮你把这段代码拆解透👇

## 一、*Handoff（任务移交）工具工厂 核心作用是什么？
这个 `create_task_description_handoff_tool` 是一个**通用工厂函数**，用来为每个目标智能体生成一个专属的「移交工具」。

它的核心目标是：
1.  让当前 Agent 可以通过调用工具的方式，把任务安全地交给下一个 Agent；
2.  同时强制传递任务描述，保证下一个 Agent 能拿到完整上下文；
3.  用 `Command` 对象通知 LangGraph 切换节点，实现流转。

简单说，就是给每个 Agent 配一个「专属转交按钮」，按一下就能把任务交给指定的 Agent。

---

## 二、逐行拆解代码逻辑
### 1. 工厂函数定义
```python
def create_task_description_handoff_tool(*, agent_name: str, description: str | None = None):
```
- `agent_name`：目标 Agent 的名字，比如 `"hotel_agent"`
- `description`：工具的描述，给 LLM 看的，用来让它知道什么时候该移交任务

### 2. 生成工具的名称和描述
```python
name = f"transfer_to_{agent_name}"
description = description or f"移交给 {agent_name}"
```
- 生成工具名 `transfer_to_hotel_agent`，LLM 能直接通过名字理解工具作用
- 描述给 LLM 看，让它知道这个工具的用途

### 3. 定义实际的 Handoff 工具
```python
@tool(name, description=description)
def handoff_tool(
    task_description: Annotated[str, "描述下一个 Agent 应该做什么，包括所有必要信息"],
    state: Annotated[MessagesState, InjectedState],
) -> Command:
```
- `task_description`：**强制参数**，要求当前 Agent 必须写清楚任务细节，再移交出去
- `state: Annotated[..., InjectedState]`：LangGraph 会自动注入当前状态，你不用传
- 返回值是 `Command`，LangGraph 会根据它切换到目标 Agent

### 4. 构建任务描述消息
```python
task_description_message = {
    "role": "user",
    "content": task_description,
}
```
把用户输入的任务描述包装成消息格式，后续会合并到状态里，传递给下一个 Agent。

---

## 三、它在多智能体里怎么用？
举个你之前看到的「旅行规划」例子：

### 1. 为每个 Agent 创建移交工具
```python
# 给主管 Agent 生成移交到酒店 Agent 的工具
transfer_to_hotel = create_task_description_handoff_tool(agent_name="hotel_agent")

# 给主管 Agent 生成移交到机票 Agent 的工具
transfer_to_flight = create_task_description_handoff_tool(agent_name="flight_agent")
```

### 2. 把工具绑定给当前 Agent
```python
supervisor_agent = create_react_agent(
    llm,
    tools=[transfer_to_hotel, transfer_to_flight]
)
```

### 3. LLM 会自动调用工具移交任务
当用户说“帮我订酒店和机票”时，主管 Agent 会先调用 `transfer_to_hotel`，把“订酒店”的任务移交出去，再调用 `transfer_to_flight` 移交订机票的任务。

---

## 四、关键优势（为什么要这么写？）
1.  **强制上下文传递**：`task_description` 参数是必填的，避免 Agent 只移交任务，却不说明情况，导致下一个 Agent 摸不着头脑。
2.  **可复用**：用工厂函数批量生成工具，新增 Agent 时不用重复写代码，一行搞定。
3.  **符合 LangGraph 规范**：通过 `Command` 对象切换节点，是官方推荐的流转方式，调试和日志都很清晰。
4.  **LLM 友好**：工具名和描述都是标准化的，LLM 能轻松理解什么时候该移交任务，不会乱调用。

## 五、适配你的编辑器项目
你可以用这个工厂函数，为每个工作者 Agent 生成移交工具：
```python
# 为图形生成 Agent 生成移交工具
transfer_to_generator = create_task_description_handoff_tool(agent_name="shape_generator")

# 为渲染 Agent 生成移交工具
transfer_to_renderer = create_task_description_handoff_tool(agent_name="svg_renderer")
```
主管 Agent 就可以根据用户指令，把任务安全地移交给生成、渲染 Agent，同时传递完整的需求描述。

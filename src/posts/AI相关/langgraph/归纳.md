# LangGraph 笔记归纳

本文档合并原 `stream`、`command`、`context`、`send`、子图、时间回溯、多智能体、`skill`、`A2A` 等分散笔记，便于一处查阅。

---

## 1. 流式输出：`stream_mode`

`graph.stream(..., stream_mode=...)` 决定客户端实时收到的数据形态，可传字符串或列表组合多种模式。

| 模式 | 含义 | 典型用途 |
| :--- | :--- | :--- |
| `values` | 每步结束推送**完整状态快照** | 需在界面重建整段上下文、多步表单 |
| `updates` | 只推送**本步状态增量** | 状态大、要省流量；前端需自行合并 |
| `messages` | LLM 的 token 流 + 元数据 | 对话「打字机」 |
| `custom` | 节点内 `StreamWriter` 的自定义内容 | 进度、步骤提示、自定义事件 |
| `debug` | 节点/状态/事件等详细日志 | 开发调试，不宜直接暴露给用户 |

**组合示例**：`stream_mode=["messages", "custom"]` 同时推模型输出与用户可见进度。

**选型**：纯对话 → `messages`；要带状态的多步流程 → `values` 或 `updates`；进度条/步骤提示 → 加 `custom`；排错 → `debug`。

## 2. `Command`：节点内更新状态并路由

`Command`（`langgraph.types.Command`）让节点**在一次返回里同时写状态和指定下一跳**，适合 LLM 决策、动态跳转、人机中断恢复，逻辑集中在节点内，减少图上条件边蜘蛛网。

**口诀**：只分流、不改状态 → 条件边；要**改状态并决定走向**、或中断恢复 → `Command`。

**常用参数**：

- `update`：合并进 state 的字典  
- `goto`：下一节点名、`END`、多节点列表（并行）、`Command.PARENT`（回到父图）等  
- `resume`：中断后恢复时传入  
- `graph`：子图相关高级用法  

最小思路：`return Command(update={...}, goto="next_node")`。  
注意与 **CLI** `langgraph new/dev/up` 区分，后者是工程脚手架与服务命令。

## 3. Runtime Context（运行时上下文）

与 **State** 的分工：

- **State**：可变业务数据，在节点间合并、演进。  
- **Runtime Context**：单次运行内相对**静态的只读依赖**（用户 ID、DB 连接、API Key、权限等），不参与 reducer 合并。

**用法概要**：

1. 用 `@dataclass` 定义上下文 schema。  
2. 建图：`StateGraph(State, context_schema=YourContext)`。  
3. 节点签名增加 `runtime: Runtime[YourContext]`，通过 `runtime.context.字段` 读取。  
4. 调用：`invoke(..., context={"user_id": "...", ...})`。

相对旧写法 `config["configurable"]`：Context 类型更清晰、子图传递更省心；执行器级别的重试/超时等仍属 `config` 范畴。

## 4. `Send`：动态并行（Map-Reduce）

`Send(node="目标节点", arg=局部状态)` 在运行时**动态生成任意多条边**，并行调用同一节点，每条任务带独立局部状态；适合「列表长度未知」的 map-reduce、发散-汇聚。

与普通静态边的区别：边数量不必预先写死，由运行时数据决定并行度。

## 5. 子图：两种接入方式与「两次合并」

**方式 A — 子图作为节点直接挂载**  
编译后的子图 `add_node("name", subgraph)`，父子常共享同一 State schema，实现快，状态自动传递。

**方式 B — 在节点函数里 `invoke` 子图**  
父子可有独立 schema，在包装节点里做输入/输出映射；隔离强，合并策略完全自控，适合私有 Agent 状态、独立 checkpoint 需求。

**`MessagesState` 子图经典坑**：子图嵌套时可能对同一字段执行**两次 reducer（如 add）**——主图→子图一次，子图结果回到主图再一次，导致 `messages` 等重复。缓解思路：父子使用不同字段、子图侧用独立列表、或改用 `Overwrite` 等策略，按业务选择是否继承主图消息。

**与多智能体**：子图适合封装单个 Agent 的工作流，主图负责调度；流水线式串行或多分支并行都可挂载多个子图。

## 6. 时间回溯（Time Travel）

依赖 **Checkpointer**（内存 / SQLite / Redis / Postgres 等）。每步执行后会生成检查点；通过 `thread_id`、`checkpoint_id` 可做：

- **历史查看**：`get_state_history`  
- **从某检查点继续执行**：在 `config.configurable` 中指定 `checkpoint_id` 再 `stream`/`invoke`  
- **分叉探索**：`get_state` → 修改 `values` → `update_state` → 再执行，形成新分支，不破坏原轨迹  

适用：调试、人工修正历史决策后重跑、多方案对比、中断续跑。无 checkpointer 则无法使用该能力。

## 7. 多智能体协作模式（概念）

| 模式 | 要点 |
| :--- | :--- |
| Network | 去中心化，任意 Agent 互连；灵活但难控、易循环 |
| Supervisor | 中心化调度，子 Agent 只与主管交互 |
| Supervisor as Tools | 子 Agent 封装成工具，主管 LLM 工具调用调度，落地快 |
| Hierarchical | 多层主管，适合超大系统 |
| Custom | 用条件边、子图、`Command` 等自由编排（实际项目常见） |

**Handoff 工厂思路**：为每个目标 Agent 生成 `transfer_to_<agent>` 类工具，强制传入 `task_description`，返回 `Command` 切换节点，保证移交时上下文完整、可与 `InjectedState` 等配合。

## 8. 附录：MCP、A2A 与 Claude Skill

**MCP（Model Context Protocol）**  
标准化「模型 ↔ 工具/数据」接入，LangGraph 节点可通过 MCP 使用外部能力。

**A2A（Agent-to-Agent Protocol）**  
标准化「智能体 ↔ 智能体」协作与发现；子图或独立服务可对外暴露为可编排的 Agent。  
二者互补：单 Agent 扩能力常用 MCP；多 Agent 互联常用 A2A；复杂系统常组合使用。

**Claude Code 的 Skill**（`SKILL.md` 等）  
是可加载的**结构化提示词/流程规范**，用于约束模型行为与输出格式，**不是**可执行函数；与 LangGraph 里「工具 = 可调用的代码」不同，勿混淆。

---

## 9. 速查

- 对话打字机 + 进度 → `messages` + `custom`  
- 路由与改状态一体 → `Command`  
- 只读依赖注入 → Runtime Context + `context_schema`  
- 动态 N 路并行 → `Send`  
- 子图重复消息 → 检查 reducer 与两次合并  
- 调试/回溯/人机改历史 → Checkpointer + 时间回溯 API

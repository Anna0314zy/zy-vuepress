## 1. 向量与 Embedding

**要解决的问题**：把非结构化文本（可扩展到图/音）映射到高维向量，使**语义相似 → 空间距离近**，从而用近邻搜索做 RAG、推荐、聚类等。

- **相似度**：常用余弦相似度，接近 1 表示更相似。  
- **与 LLM 分工**：Embedding 负责「表示与检索」；LLM 负责「生成」。可记：**Embedding = 搜索侧，LLM = 生成侧**。  
- **RAG 主路径**：问题向量化 → 向量库 Top-K → 将片段作为上下文喂给 LLM 生成回答。  
- **向量库常见索引思路**：HNSW、IVF、乘积量化（PQ）等，目标是在大规模向量上快速近邻搜索。  
- **工程注意**：Embedding 质量决定检索与 RAG 上限；同一业务尽量固定同一套 embedding 模型，便于向量空间一致。

**云 API 使用思路**（具体 SDK 以各平台文档为准）：

- 国内常用阿里云 DashScope `text-embedding-v3` 等；海外常用 OpenAI `text-embedding-3-small` 等。  
- 进阶能力：批量请求、失败重试、多模态 embedding、与向量库/Redis Stack 组合。原「向量1 / 向量2」中的长代码可迁到独立仓库或从版本历史恢复。

## 2. Runnable：什么时候用哪种组合

| 模式 | 典型场景 |
| :--- | :--- |
| **Sequence**（`\|` 串联） | 固定流水线：预处理 → 填槽 → 模型 → 解析 |
| **RunnableBranch** | 需要 if/else：按类型/语言走不同子链 |
| **RunnableParallel** | 同一次要同时产出多路（如标题+正文+摘要），类似 `Promise.all` |
| **RunnableLambda** | 非模型逻辑：截断、拼字符串、清洗结构 |

现实链往往是：**Lambda 预处理 → Branch 选路 → Parallel 多段生成 → 再 Sequence 后处理**。与前端类比：Sequence ≈ 中间件管道，Branch ≈ 路由，Parallel ≈ 并发任务。

## 3. RAG：文本分割（Text Splitter）

**基类常见方法**：`split_text`、`split_documents`、`create_documents`。

| 分割器 | 适用 |
| :--- | :--- |
| `RecursiveCharacterTextSplitter` | 通用首选，按分隔符优先级递归切 |
| `CharacterTextSplitter` | 规则简单、分隔符明确 |
| `MarkdownHeaderTextSplitter` | 按 MD 标题保留结构 |
| `PythonCodeTextSplitter` | 代码知识库，减少「半段函数」 |
| `TokenTextSplitter` | 需严格按 token 对齐模型窗口 |
| `HTMLHeaderTextSplitter` | 网页/按 h1–h3 结构 |

**`RecursiveCharacterTextSplitter` 要点**：

- `chunk_size` / `chunk_overlap`：中文常从 512–1024 与约 10%–20% overlap 起调；过小易碎、过大易混主题。  
- `separators`：中文建议包含 `"\n\n"`, `"\n"`, `。`, `，`, 空格等，**不要**默认只按英文空格切。  
- 需与 token 对齐时，用 `tiktoken` 等做 `length_function`。

**避坑**：代码块不要用通用切分硬切；`TokenTextSplitter` 与「字符长度」不是一一对应，不要混用估算方式。

## 4. Memory：聊天历史与 `RunnableWithMessageHistory`

- **`BaseChatMessageHistory`**：存储抽象，需实现 `add_message` / `clear` 等；实现类包括内存、文件、Redis、ES 等。  
- **`RunnableWithMessageHistory`**：在链外自动拉取历史、注入 prompt、写回新消息；调用时通过 `config["configurable"]["session_id"]` 区分会话。  
- **理解**：LLM 本身无状态，**Memory = 外挂状态**；与「仅自己在 prompt 里拼 history 字符串」相比，可插拔存储、边界更清晰。

## 5. Redis 与 Redis Stack

- **普通 Redis**：KV、缓存、锁、计数、Pub/Sub 等。  
- **Redis Stack**：在 Redis 上集成 **RediSearch（全文/向量）**、**RedisJSON**、时序、图、Bloom 等模块，适合知识库、轻量向量检索、JSON 文档。  
- **与当前学习路径结合**：聊天历史可落 Redis；文档可 JSON 存 + 搜索/向量；与 LangChain 的 Memory、向量存储对接。  
- **学习顺序建议**：基础命令 → RedisJSON → RediSearch → 向量索引（KNN）→ 再接到 LangChain。Docker 可一行起 `redis/redis-stack` 开发环境（见各官方文档）。

## 6. LangGraph：学习路线、课表、面试题

**与 `../langgraph/归纳.md` 的分工**：运行时代码级概念（`stream_mode`、`Command`、`Send`、Runtime Context、子图两次合并、Time Travel 等）以该篇为准；下表帮助**排课与面试**。

### 6.1 分阶段学习路线（简版）

1. **基础**：定位、与线性 Chain 差异、State / Node / Edge、HelloWorld、五步法。  
2. **API**：`StateGraph`、边与条件边、TypedDict / Pydantic、Reducer、Node 缓存与重试、**Send 并行**。  
3. **进阶**：Command、Runtime Context、流式、Checkpointer（内存 → SQLite）、记忆与时间回溯、子图。  
4. **多智能体**：跨图状态、Supervisor-Worker、A2A/路由、技能模块化。

### 6.2 课程单元与要点（与视频/资料编号对应）

### 6.3 LangGraph 高频面试题（精简答）

1. **LangGraph 是什么**：有状态图编排，适合分支、循环、持久化、中断与复杂 Agent。  
2. **与 Chain 区别**：Chain 偏线性无状态；图支持状态、条件、检查点、回溯。  
3. **四要素**：State、Node、Edge、Graph。  
4. **State 作用**：全图共享、随执行演化的数据模型。  
5. **更新机制**：节点返回增量，框架合并。  
6. **State 定义**：TypedDict 轻量；Pydantic 强校验。  
7. **Reducer**：同名字段的合并策略（如 `operator.add` 追加列表）。  
8. **Annotated + operator.add**：消息列表追加而非覆盖。  
9. **Node**：最小执行单元；宜保持可测、少副作用。  
10. **Node 形式**：函数或可调用对象。  
11. **缓存**：避免重复调 LLM/工具。  
12. **重试**：网络类节点提高稳定性。  
13. **普通边 vs 条件边**：固定下一跳 vs 按状态路由。  
14. **START / END**：图入口与结束标记。  
15. **Send**：动态多路并行、map-reduce 等（细节见 `../langgraph/归纳.md`）。  
16. **Checkpointer**：状态快照；Memory / SQLite 等实现。  
17. **Time-Travel**：基于检查点回放与分支调试。  
18. **子图**：复用与分层，注意与父图状态合并策略。  
19. **Command**：同时更新状态并指定下一跳。  
20. **多智能体**：Supervisor-Worker 最常见；另有 A2A、路由等。

# setState

setState 在 React 中是批处理的。批处理的本质是通过 executionContext 上下文标记来控制更新时机。

React 17 及之前，只在合成事件和生命周期函数内部进行批处理，而在 setTimeout、Promise、原生事件等场景不会批处理，需要手动使用 unstable_batchedUpdates。

React 18 引入了自动批处理，通过 createRoot 创建的渲染树，无论是合成事件、异步回调还是 Promise，都会自动合并更新，始终只触发一次重新渲染。如果需要退出批处理，可以使用 flushSync。

从源码层面看，setState 调用后会调用 enqueueUpdate 将更新放入队列，然后根据 executionContext 决定是等批量更新还是立即刷新。

# useEffect闭包

useEffect 闭包陷阱是指 useEffect 中的回调函数会捕获定义时的变量值，即使组件重新渲染、变量更新，effect 内部访问的仍然是旧值。

这本质上是由 JavaScript 闭包机制导致的：useEffect 的回调函数在创建时会捕获当前作用域中的所有变量。如果依赖数组为空，这个函数永远不会被重新创建，因此永远持有初始值。

解决方案有四种：

正确声明依赖：将使用到的变量加入依赖数组，但这可能导致 effect 频繁重建

函数式更新：对于状态更新，使用 setState(prev => prev + 1) 避免依赖外部值

useRef 存储最新值：用 ref 保存最新值，effect 中通过 ref.current 访问

useReducer：将复杂状态逻辑抽离，dispatch 函数是稳定的

从源码角度看，这个问题源于 Hooks 链表机制：effect 函数在 mount 时创建并存储，update 时如果依赖不变就直接复用，不会重新创建闭包。React 团队推荐使用 ESLint 规则 exhaustive-deps 来自动检测并警告这类问题。

# useMemo use

```text
是否需要 useMemo/useCallback？
                │
                ▼
        计算是否昂贵？ ──是──→ 用 useMemo
         (< 1ms 不算昂贵)     │
               否             │
                ▼             │
        返回值是否作为      │
        其他 Hook 依赖？ ──是──┤
               否             │
                ▼             │
        传递给 React.memo   │
        子组件的 props？ ──是──┼─→ 用 useCallback（函数）
               否             │   用 useMemo（对象/数组）
                ▼             │
               都不需要         │
                │             │
                ▼             ▼
           不要用！        可以用！

```

这两个 Hook 主要用于性能优化，核心目的都是缓存，避免不必要的重复计算或重渲染。

useMemo 的使用场景：

缓存昂贵的计算结果（如大数据量的过滤、排序）

稳定对象/数组的引用，配合 React.memo 避免子组件重渲染

作为其他 Hook（如 useEffect）的依赖项，避免 effect 频繁执行

useCallback 的使用场景：

传递给 React.memo 子组件的回调函数，保持引用稳定

作为 useEffect 的依赖项，避免无限循环或频繁执行

在深层组件树中传递事件处理函数

不应该使用的场景：

计算非常简单（如算术运算、字符串拼接）

没有使用 React.memo 的子组件

传递给原生 DOM 元素的事件

核心原则是：只有在真正产生性能问题时才使用，滥用反而会增加内存开销和代码复杂度。React 官方也强调，多数情况下不需要手动优化，React 本身已经很快了。

# hook使用

为什么 Hooks 不能写在条件判断里？

答：这是因为 React Hooks 的实现依赖于固定的调用顺序。

从源码层面看，每个函数组件对应一个 Fiber 节点，其 Hooks 以链表形式存储在 fiber.memoizedState 上。首次渲染时，React 会按照 Hooks 的调用顺序依次创建 Hook 节点并链接成链表。后续渲染时，React 会按照完全相同的顺序从链表中依次读取对应的状态。

如果 Hooks 写在条件判断中，不同渲染条件下 Hooks 的调用次数和顺序可能会不同，导致：

链表索引错位，状态读取错误

可能读取到其他 Hook 的状态

状态更新函数对应错误的状态值

可能导致难以调试的 bug 或崩溃

React 团队在设计时就明确了这个约束，并通过 ESLint 插件 react-hooks/rules-of-hooks 来强制检查，确保所有 Hooks 都在组件顶层调用。这是 React Hooks 的核心设计决策，没有例外。

如果需要在条件中使用 Hook，正确的做法是始终调用 Hook，然后在 Hook 内部或使用条件语句来处理逻辑。

# React 中如何实现动态组件？

答：React 中实现动态组件主要有三种方式：

条件渲染：通过 JavaScript 条件判断或对象映射，在运行时选择要渲染的组件。这是最基础的方式，适合组件数量少、切换不频繁的场景。

React.lazy + Suspense：这是 React 官方推荐的代码分割方案。lazy 函数接收一个动态 import() 函数，返回一个可以在 Suspense 中使用的组件。当组件渲染时，React 会自动加载对应的代码块，加载期间显示 Suspense 的 fallback。这种方式可以将初始包体积减少 30-60%。

组件注册表模式：预先定义组件名到动态导入函数的映射，根据配置动态渲染。常用于 CMS 系统、可视化搭建平台等需要灵活配置的场景。

从源码角度，React.lazy 返回一个特殊的 React 元素类型（REACT_LAZY_TYPE），内部维护加载状态（pending/resolved/rejected）。首次渲染时会触发动态导入，并抛出 Promise 给 Suspense 捕获；加载完成后触发重新渲染，此时返回真实的组件。

需要注意：动态组件应该配合 ErrorBoundary 处理加载失败，使用 Webpack Magic Comments 优化打包，在 SSR 场景下需要特殊处理（如 Next.js 的 dynamic 函数）。
# React 中的不可变是什么意思？为什么重要？

不可变是指数据一旦创建就不能被修改，任何变化都需要创建全新的数据。

React 之所以强调不可变，是因为它使用浅比较（引用比较）来判断状态是否变化。当调用 setState 或 dispatch 时，React 会比较新旧状态的引用：

如果引用相同，React 认为状态没变，不会重新渲染

如果引用不同，React 认为状态变了，触发重新渲染

如果直接修改状态（可变操作），虽然数据实际上变了，但引用没变，React 检测不到变化，导致界面不更新。

另外，不可变数据还有其他好处：

更容易调试（可以记录每次变化）

更容易实现时间旅行（撤销/重做）

避免意外的副作用

配合 React.memo 可以优化性能

# Immer 的实现原理

答：Immer 的核心原理是 Proxy 代理 + 写时复制（Copy-on-Write）。

具体流程分为三步：

代理阶段：Immer 对原始数据创建 Proxy 代理，生成一个"草稿"（Draft）。这个代理会拦截所有读写操作。

修改阶段：用户在草稿上直接修改数据。Proxy 会记录哪些属性被修改了：

读取属性时，如果没修改过，返回原始值并深层代理

写入属性时，标记当前节点为"已修改"，并创建浅拷贝（copy），将修改应用在 copy 上

修改会向上传播，父节点也会被标记为已修改

生成阶段：produce 执行完后，遍历整个代理树：

如果节点没被修改，直接复用原对象（结构共享）

如果节点被修改了，用 copy 替换，并递归处理子节点

最终生成一个全新的不可变对象

这种设计的优势是：

性能好：只复制被修改的路径，未修改部分共享引用

API 友好：用户可以用可变语法写不可变逻辑

自动冻结：开发环境返回的对象会被冻结，防止意外修改

核心源码主要体现在 Proxy 的 get、set、deleteProperty 三个拦截器上，以及 produce 函数对执行流程的整体控制。


------

当修改深层属性时，Immer 会：

通过 Proxy 追踪所有修改操作

从修改点向上，标记所有祖先节点为"已修改"

在 finalize 阶段，只为"已修改"的节点创建浅拷贝

未被标记的节点直接共享原对象

这样，每个被修改的节点都是通过浅拷贝创建的，而它们的子节点要么继续共享原始对象（未修改），要么也通过浅拷贝创建（被修改了）。递归执行这个策略，最终得到一株全新的树，其中只有路径上的节点是新对象，其他都是共享的。

这种设计的精妙之处在于：浅拷贝保证了创建新节点的性能开销很小，而路径复制保证了只复制必要的节点。如果使用深拷贝，虽然实现简单，但性能会差很多，特别是对大型嵌套对象。

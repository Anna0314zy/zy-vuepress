# 🧠 React 更新

---

# 1. React 到底在解决什么问题？

一句话：

> React 解决的是“UI 随状态变化如何高效更新”的问题。

传统方式的问题：

* 直接操作 DOM（jQuery）
* 手动维护状态 → 容易错
* DOM 更新成本高

---

## ✔ React 的核心目标

React 想做三件事：

1. **描述 UI（声明式）**
2. **自动计算变化（Diff）**
3. **高效更新 DOM**

---

# 2. React 的整体架构（必须先背）

React 分三层：

```txt id="arch1"
Scheduler（调度层）
↓
Reconciler（Fiber diff）
↓
Renderer（DOM / Native）
```

---

## ✔ 三层职责

### ① Scheduler（调度）

决定：

> “什么时候更新”

---

### ② Reconciler（Fiber）

决定：

> “更新什么”

---

### ③ Renderer（react-dom）

决定：

> “怎么更新 DOM”

---

# 3. React 更新的完整流程（核心链路）

必须背这个：

```txt id="flow"
setState
  ↓
scheduleUpdateOnFiber
  ↓
Scheduler 调度
  ↓
render 阶段
    → beginWork（向下 diff）
    → completeWork（向上构建）
  ↓
commit 阶段（更新 DOM）
```

---

# 4. Fiber 是什么？（核心本质）

一句话：

> Fiber 是 React 的“最小工作单元”

---

## ✔ Fiber 本质结构

```js id="fiber"
Fiber = {
  type,          // div / Component
  props,

  child,
  sibling,
  return,

  alternate,     // 上一次渲染结果
  effectTag      // 标记：增/改/删
}
```

---

## ✔ Fiber 的关键能力

* 可中断
* 可恢复
* 可拆分任务
* 可优先级调度

---

# 5. 为什么需要 Fiber？（核心原因）

## ❌ 以前（递归）

React 15：

```txt id="rec"
递归 diff 整棵树
→ 一次性执行
→ 不能暂停
```

问题：

* 卡顿
* 无法插队
* 无法拆任务

---

## ✔ Fiber（现在）

```txt id="fiberflow"
循环执行 work unit
→ 每个 Fiber 是一个任务
→ 可以暂停
→ 可以继续
```

---

# 6. render 阶段（可中断）

React 的核心创新：

> render 阶段可以随时暂停

---

## ✔ 执行模型

```js id="workloop"
while (nextUnitOfWork) {
  performUnitOfWork()
}
```

---

## ✔ 两个关键函数

### ① beginWork（向下）

作用：

* 计算当前节点
* diff 子节点

---

### ② completeWork（向上）

作用：

* 创建 DOM
* 收集 effect

---

## ✔ render 特点

* ❌ 不操作 DOM
* ✔ 可以暂停
* ✔ 可以重来

---

# 7. commit 阶段（不可中断）

React 第二阶段：

> 一次性更新 DOM

---

## ✔ commit 做什么

* 插入 DOM
* 更新 DOM
* 删除 DOM

---

## ✔ 为什么不能中断？

因为：

> DOM 更新必须保持一致性

---

# 8. Diff（reconcile）算法

React diff 核心规则：

---

## ✔ 同层比较

只比较同一层节点

---

## ✔ type 相同复用

```txt id="diff"
div → div = 复用
div → span = 替换
```

---

## ✔ key 用于列表优化

---

## ✔ 本质一句话

> React diff = 同层 + 类型比较 + key优化

---

# 9. Scheduler（并发核心）

React 为什么不卡？

因为 Scheduler：

---

## ✔ 核心机制

* 时间切片（time slicing）
* shouldYield（让出线程）
* 优先级调度

---

## ✔ 本质

> 把“长任务”拆成“多个小任务”

---

# 10. Hooks（React 状态系统）

Hooks 本质不是魔法：

---

## ✔ 本质结构

```txt id="hooks"
fiber.hooks = [hook0, hook1, hook2]
```

---

## ✔ useState 做了什么

* 记录 state
* 维护 queue
* setState → 触发重新 render

---

## ✔ 一句话

> Hooks = fiber 上的数组状态 + index 顺序机制

---

# 11. React 为什么快？（必考）

必须这样回答：

---

## ✔ 4个核心原因

### ① Fiber 可中断渲染

避免卡顿

---

### ② Scheduler 调度任务

控制优先级

---

### ③ render / commit 分离

保证一致性

---

### ④ diff 只做必要更新

减少 DOM 操作

---

# 12. React 的本质总结（最重要）

一定要会这句话：

> React 是一个“基于 Fiber 的可中断调度系统”，通过 Scheduler 控制更新时机，通过 Reconciler 计算变化，通过 Renderer 更新 DOM。

## 三、双缓存树切换图（重点理解）

```
【更新前】                              【Render 阶段】
                                        
    current 树                         workInProgress 树
    (正在显示)                          (内存中构建)
                                        
    ┌─────┐                            ┌─────┐
    │ App │                            │ App │ ← 基于 current 克隆
    └──┬──┘                            └──┬──┘
       │                                   │
    ┌──┴──┐                             ┌──┴──┐
    │ div │                             │ div │
    └──┬──┘                             └──┬──┘
       │                                   │
    ┌──┴──┐                             ┌──┴──┐
    │ h1  │                             │ h1  │
    └─────┘                             └─────┘
                                        
    alternate 指针互相指向对方


【Commit 阶段最后一步】                  【更新后】

    root.current ──→ finishedWork          current 树
                                           (新 UI)
         │                                        
         └──────────────┐                  ┌─────┐
                        ▼                  │ App │
    workInProgress 树   │                  └──┬──┘
    (变成新的 current)  │                     │
                        │                  ┌──┴──┐
    ┌─────┐             │                  │ div │
```

## 四、一句话串联（背这个）

> **调度定优先级，render 走链表；begin 向下问复用，complete 向上造 DOM；effect list 串起副作用，commit 三小步：前置快照、核心 DOM、后置生命周期；最后指针一交换，新 UI 呈现屏幕前。**

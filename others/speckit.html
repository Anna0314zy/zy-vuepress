Spec-Driven Development

从 Vibe Coding 到规范驱动开发的演进

AI 编程的现状

2025 年，AI 编程已成为主流

惊人的数据

  • Y Combinator 2025 冬季批次中
  • 25% 的项目代码库
  • 95% 由 AI 生成
— Garry Tan (YC CEO), 2025

Vibe Coding 时代

"Vibe Coding" 一词由 Andrej Karpathy 于 2025 年 2 月提出

— 前 Tesla AI 总监、OpenAI 联合创始人

什么是 Vibe Coding?

用户: 帮我写一个登录页面

AI: 好的，这是一个登录页面...
    [生成代码]

用户: 再加个注册功能

AI: 好的，我来添加...
    [修改代码]

用户: 样式不对，改一下

AI: 好的...

即兴式的 AI 对话开发

---

Vibe Coding 的问题

当项目规模增长时，问题开始显现

技术债务

  • 代码不够整洁、可维护
  • 难以复用
  • 缺乏统一架构

调试困难

  • AI 生成的代码难以理解
  • 缺少上下文信息
  • Bug 定位困难

性能问题

  • 缺乏全局优化视角
  • 重复代码多
  • 资源浪费

缺乏全局视野

  • 每次对话都是孤立的
  • AI 不知道整体目标
  • 容易偏离方向

layout: center

解决方案：Spec-Driven Development

"先写规范，再写代码"

规范驱动开发不是写代码后补文档

而是先定义规范，让 AI 基于规范生成代码

📋
Specification
定义做什么、为什么
📐
Plan
设计如何实现
✅
Tasks
拆分可执行任务

GitHub Spec Kit 介绍

GitHub 开源的规范驱动开发工具包

是什么？

Spec Kit 是一套约定和模板，用于以 AI 工具可理解的方式描述软件项目

  • 开源工具包
  • 支持多种 AI 工具
  • 结构化的开发流程

支持的工具

  • GitHub Copilot / Claude Code
  • Gemini CLI / Cursor / 更多...

核心理念

graph TD
    A[Constitution] --> B[Specify]
    B --> C[Plan]
    C --> D[Tasks]
    D --> E[Implementation]
    E -.-> B

循环迭代的开发流程

项目结构

.specify/
├── memory/
│   └── constitution.md    # 项目宪法
├── scripts/
│   └── *.sh               # 辅助脚本
├── specs/
│   └── 001-feature/
│       ├── spec.md        # 功能规范
│       ├── plan.md        # 实现计划
│       └── tasks.md       # 任务列表
└── templates/
    └── *.md               # 文档模板

核心文件

文件作用
constitution.md项目宪法（核心原则）
spec.md功能规范（What & Why）
plan.md实现计划（How）
tasks.md任务列表（Execute）

核心概念 1: Constitution

项目宪法 - 不可违背的核心原则

什么是 Constitution?

Constitution 定义了项目的非可协商原则

  • 技术栈选择
  • 架构约束
  • 代码风格
  • 安全要求

为什么需要？

  • 保持项目一致性
  • 避免 AI 偏离方向
  • 团队共识的载体

示例

# Project Constitution

## Technology Stack
- TypeScript 5.x + Node.js 20+
- React 18+ (functional components)

## Architecture
- State: Zustand, API: React Query

## Code Standards
- ESLint + Prettier, no `any`

## Security
- No secrets in code

核心概念 2: Specify

定义功能的 What 和 Why

规范包含什么？

  • 目标 - 要解决什么问题
  • 用户故事 - 谁需要、需要什么
  • 验收标准 - 怎样算完成
  • 约束条件 - 限制和边界
  • 成功指标 - 如何衡量

命令

/speckit.specify

示例: spec.md

# User Authentication

## Goal
Enable secure authentication with
email/password and social login.

## User Stories
- Register with email
- Login with Google

## Acceptance Criteria
- [ ] Email validation
- [ ] OAuth 2.0 social login

## Constraints
- GDPR compliance required

核心概念 3: Plan

定义功能的 How

计划包含什么？

  • 技术方案 - 选用什么技术
  • 架构设计 - 组件如何组织
  • 数据流 - 数据如何流转
  • API 设计 - 接口定义
  • 依赖关系 - 需要什么前置

命令

/speckit.plan

示例: plan.md

# Dashboard Component Plan

## Technical Approach
- React 18 + TypeScript
- Zustand for state management
- TailwindCSS for styling

## Component Structure
App → Layout → Dashboard → Cards

## Key Components
- <DashboardLayout />
- <StatCard />
- <ChartWidget />

核心概念 4: Tasks

将计划拆分为可执行的任务

任务特点

  • 原子性 - 每个任务独立完成
  • 依赖明确 - 清晰的前置关系
  • 可并行 - 标记 [P] 可并行执行
  • 可验证 - 有明确的完成标准

命令

/speckit.tasks

执行阶段

  1. Setup - 环境准备
  2. Tests - 测试先行
  3. Core - 核心实现
  4. Integration - 集成联调
  5. Polish - 优化完善

示例: tasks.md

# Dashboard Tasks

## Phase 1: Setup
- [x] 1.1 Init project structure
- [x] 1.2 Install dependencies

## Phase 2: Components
- [ ] 2.1 Create DashboardLayout
- [P] 2.2 Build StatCard (depends: 2.1)
- [P] 2.3 Build ChartWidget (depends: 2.1)

## Phase 3: Polish
- [ ] 3.1 Add animations
- [ ] 3.2 Write tests

完整工作流程

flowchart LR
    A[Constitution] --> B[Specify] --> C[Plan] --> D[Tasks] --> E[Implement]
    E -.-> B
1. Constitution
定义项目原则
2. Specify
定义功能需求（What & Why）
3. Plan
设计技术方案（How）
4. Tasks
拆分执行任务（Execute）
specify init → /speckit.specify → /speckit.plan → /speckit.tasks → /speckit.implement

核心命令一览

命令作用产出
/speckit.constitution创建/更新项目宪法constitution.md
/speckit.specify定义功能规范spec.md
/speckit.clarify澄清规范中的模糊点更新 spec.md
/speckit.plan生成实现计划plan.md
/speckit.tasks生成任务列表tasks.md
/speckit.implement执行任务实现代码文件
/speckit.analyze跨文档一致性检查分析报告
/speckit.checklist生成自定义检查表检查清单

快速开始

1. 初始化项目

uvx --from git+https://github.com/github/spec-kit.git specify init my-project

2. 开发流程

定义需求
/speckit.specify
将需求转化为结构化规范
设计方案
/speckit.plan
生成详细的实现计划
生成任务
/speckit.tasks
拆分为可执行的任务列表
开始实现
/speckit.implement
按任务逐步编写代码

Vibe Coding vs SDD

两种开发范式的对比
❌ Vibe Coding
用户: 写个待办事项应用
AI: [直接生成代码...]
用户: 加个截止日期
AI: [修改代码...]
用户: 支持多用户
AI: [大改代码...]
用户: 怎么之前的功能坏了？
AI: 让我看看...
⚠️ 缺乏全局视野，改动累积导致混乱
✅ Spec-Driven Development
用户: 写个待办事项应用
AI: 让我先理解需求... → spec.md
用户: 确认，加上多用户支持
AI: 更新规范 → plan.md
用户: 看起来不错
AI: 生成任务 → tasks.md
用户: 开始吧
AI: [按任务顺序实现...]
✓ 清晰的规范，有序的实现，可追溯

SDD 的核心优势

👨‍💻 对开发者
✓
减少猜测 - AI 清楚知道要做什么
✓
减少“惊喜” - 严格按规范执行
✓
更高质量 - 有明确验证标准
✓
更快上手 - 读规范即可理解项目
👥 对团队
✓
统一共识 - 规范即文档，无歧义
✓
可追溯 - 所有决策有记录
✓
可复用 - 模板和模式标准化
✓
可协作 - 支持并行开发

SDD 的挑战

规范驱动开发也有其困难

人的因素

"问题不在 AI，而在人"

  • SDD 要求开发者精确表达意图
  • 写好规范需要技能
  • 沟通能力成为核心竞争力

"未来最有价值的程序员是沟通能力最强的人"
— Sean Grove, OpenAI

学习曲线

  • 需要学习新的工作流
  • 模板和规范的理解成本
  • 从 "直接写代码" 到 "先写规范" 的思维转变

额外开销

  • 前期规范投入时间
  • 维护规范与代码同步
  • 小项目可能得不偿失

适用场景: 中大型项目、团队协作、需要长期维护的项目

核心观点

"规范，而非提示词或代码，正在成为编程的基本单元"

从 Vibe Coding 一个酷炫的应用，到构建真实世界的棕地项目，
规范驱动开发不是选择，而是必然。

最佳实践

📝 规范编写
1.
先 Why 后 What
解释背景动机，再描述具体需求
2.
具体而非模糊
❌ "系统要快" → ✅ "API < 200ms"
3.
验收标准可测试
每条标准可验证，自动化测试对应
4.
保持更新
规范随需求演进，代码与规范同步
📋 任务拆分
1.
原子化
每个任务 2-4 小时，独立可完成
2.
依赖清晰
明确前置任务，避免循环依赖
3.
并行标记
可并行任务标 [P]，提高效率
4.
测试先行
先写测试任务，再写实现任务
💡 核心原则： 规范是"活文档"，随项目演进持续更新
